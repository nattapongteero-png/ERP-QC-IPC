1 การคืนวัตถุดิบ (Material Return) หลังชั่งไม่หมด

⚠ บางส่วน
หัวข้อ รายละเอียด
ประเด็น / ความต้องการ เมื่อ Operator เบิกวัตถุดิบจากคลัง 100g แต่ชั่งใช้จริงเพียง 95g ต้องมีกระบวนการคืน 5g กลับคลัง พร้อม audit trail เพื่อให้ระบบ stock ตรงความจริงและตรวจสอบย้อนหลังได้ตาม GMP
สิ่งที่ระบบมีแล้ว
  • inventory_transactions รองรับ type 'RETURN' แล้ว
  • ระบบตัด stock ตาม weighedQty (ไม่ใช่จำนวนที่เบิก)
  • Audit trail framework พร้อมใช้ (audited-wrapper.ts)
  • Dual-control pattern ในการ verify
สิ่งที่ระบบยังไม่มี
  • ฟิลด์ returnedQty, returnedAt, returnedBy, returnReason ใน work_order_materials
  • Status enum value 'returned'
  • หน้า UI /production/work-orders/[id]/material-return
  • API orchestration เชื่อมการคืนกับ Work Order
  • Dual control enforcement (Operator คืน, Warehouse Staff รับคืน)
สิ่งที่ต้องพัฒนา
  • Schema migration (SQLite + MySQL) — เพิ่ม 4 ฟิลด์
  • API: POST /api/production/work-orders/[id]/materials/[mid]/return
  • Modal UI "🔄 คืน X g กลับคลัง" ในหน้า material-weighing
  • Dual control signing + audit log integration
  • Unit test + E2E test
⏱ ประมาณการเวลาพัฒนา 12 ชั่วโมง (1.5 วัน)

2 การตรวจจับ Variance (ชั่งไม่ตรงแผน)

✗ ไม่ผ่าน GMP
หัวข้อ รายละเอียด
ประเด็น / ความต้องการ เมื่อ Operator ชั่งวัตถุดิบเกิน/ต่ำกว่าจำนวนที่ plan ระบบต้องแจ้งเตือน บังคับกรอกเหตุผล (deviation reason) และส่ง QA อนุมัติก่อนใช้งาน ตามมาตรฐาน GMP สำหรับ active ingredients
สิ่งที่ระบบมีแล้ว
  • UI แสดงกรอบสีเหลืองเมื่อ |variance| > 5% (ข้อความ "ส่วนต่างสูง - กรุณาตรวจสอบ")
  • คำนวณ variance ในรายงาน WO detail (variance = actualQty - plannedQty)
  • โมดูล Deviation Management มีอยู่แล้ว (/quality/deviations/) แต่ไม่ถูกเชื่อม
สิ่งที่ระบบยังไม่มี
  • Backend validation - API รับค่าชั่งใดๆ ก็ได้ ไม่บล็อก
  • Modal บังคับกรอกเหตุผลเมื่อเกิน tolerance
  • Verify button ไม่บล็อก - ชั่งเกิน 20% ก็กด Verify ผ่านได้
  • ฟิลด์ toleranceLow, toleranceHigh, deviationReason, deviationId, qaApprovedBy ใน work_order_materials
  • Link ไปยัง Deviation module สำหรับ QA approval
  • Audit log action marker WEIGHING_VARIANCE_EXCEED
สิ่งที่ต้องพัฒนา
  • Schema migration - เพิ่ม 5 ฟิลด์ + tolerance master data ที่ BOM line
  • Backend validation service reject หากเกิน ±10% (ค่าตั้งต้น ปรับได้)
  • Deviation reason modal + QA notification
  • Auto-create Deviation record เชื่อมกับ /quality/deviations/
  • Disable Verify button จนกว่า QA จะ approve
  • รายงาน Variance Summary per WO + Dashboard KPI
  • Unit test + E2E test
⏱ ประมาณการเวลาพัฒนา 16 ชั่วโมง (2 วัน)

3 SOP Step ↔ IPC Integration

✗ ไม่ผ่าน GMP
หัวข้อ รายละเอียด
ประเด็น / ความต้องการ ใน SOP Template ต้องกำหนดได้ว่าขั้นตอนใดต้องทำ IPC (In-Process Control) และในหน้าบันทึก SOP Step ต้องมี link ไปยังหน้าบันทึก IPC สำหรับ step นั้นๆ โดยตรง
สิ่งที่ระบบมีแล้ว
  • ตาราง bom_sop_steps เก็บ SOP steps ต่อ BOM
  • ตาราง bom_in_process_qc เก็บ IPC criteria ต่อ BOM (ระดับ BOM)
  • หน้าบันทึก SOP Execution (/work-orders/[id]/sop-execution)
  • หน้าบันทึก IPC (/work-orders/[id]/ipc)
  • Master data IPC Criteria (/master-data/ipc-criteria/)
สิ่งที่ระบบยังไม่มี
  • ฟิลด์ ipcCriteriaIds (JSON array) ใน bom_sop_steps
  • UI เลือก IPC criteria ต่อ SOP Step ในหน้า BOM Configuration
  • Badge "🔬 IPC Required" บน SOP step card
  • ปุ่ม "บันทึก IPC" บน step card เชื่อมไปหน้า IPC พร้อม pre-select step
  • Deep-link /ipc?stepId=X พร้อม filter IPC tests
  • Logic บล็อก step verify ถ้า IPC ที่ required ยังไม่ผ่าน
สิ่งที่ต้องพัฒนา
  • Schema migration - เพิ่ม ipcCriteriaIds ใน bom_sop_steps (SQLite + MySQL)
  • Multi-select IPC criteria ใน SOP Step form (BOM Configuration)
  • Badge + ปุ่ม "บันทึก IPC" ในหน้า SOP Execution
  • Deep-link + pre-filter ในหน้า IPC
  • API auto-create wo_ipc_tests records จาก step → ipcCriteriaIds
  • Gate step verify ตาม IPC pass/fail status
  • Unit test + E2E test
⏱ ประมาณการเวลาพัฒนา 14 ชั่วโมง (1.5-2 วัน)

4 IPC — Criteria Type ใหม่ + Bulk Pass/Fail + UI Redesign

✗ ไม่มีในระบบ
หัวข้อ รายละเอียด
ประเด็น / ความต้องการ 4.1 เพิ่ม Criteria Type ใหม่ "ผ่าน/ไม่ผ่าน แบบระบุจำนวน" — กำหนด sample size เช่น 20 เม็ด, ระบุผ่าน 17 เม็ด ไม่ผ่าน 3 เม็ด (ช่อง auto-calc ซึ่งกันและกัน ห้ามระบุเกิน sample size)
4.2 เปลี่ยนชื่อ Criteria Type เดิม "ผ่าน/ไม่ผ่าน (checkbox)" → "ผ่าน/ไม่ผ่าน checkbox (ตรวจสอบแต่ละ sample)" เพื่อแยกความหมายจาก type ใหม่
4.3 ในหน้าบันทึก IPC (ตรวจลักษณะภายนอก) ต้องมีปุ่ม "All Pass" / "All Fail" bulk action เลือกได้พร้อมกันทุกตัวอย่าง + ปรับ design หน้าจอการบันทึกให้กระชับ
สิ่งที่ระบบมีแล้ว
  • Criteria Type ปัจจุบัน 2 แบบ: numeric (กรอกค่าตัวเลข) และ checkbox (Pass/Fail ต่อ sample)
  • ฟิลด์ sampleSize, tolerancePercent ใน ipc_criteria
  • หน้าบันทึก checkbox IPC แสดง grid 5 columns + sequential fill (ต้องกดทีละ sample)
  • สรุป "ผ่าน X/Y ตัวอย่าง (pass%)" และ tolerance check
  • Master Data IPC Criteria form + ipc_test_samples table ครบ
สิ่งที่ระบบยังไม่มี
  • Criteria Type "count_based" (ระบุจำนวนผ่าน/ไม่ผ่านแบบรวม ไม่ต้องเช็คทีละ sample)
  • ฟิลด์ passCount, failCount ใน ipc_criteria table
  • Logic auto-calc ใน Form: ระบุ pass = 17 ให้ fail auto = 3 (sample_size - pass)
  • Validation: pass + fail ห้ามเกิน sampleSize
  • ปุ่ม "All Pass" / "All Fail" ในหน้า IPC Recording (บังคับกดทีละ sample)
  • Section "ตรวจลักษณะภายนอก" (visual/appearance) แยกออกมาเฉพาะ — ปัจจุบันใช้ checkbox grid ร่วมกับ IPC อื่น
  • UI redesign หน้าบันทึก IPC (header sticky, compact summary bar, group by criteria type)
  • การเปลี่ยนชื่อ label "checkbox" → "checkbox (ตรวจสอบแต่ละ sample)" ใน UI + master data
สิ่งที่ต้องพัฒนา
  • Schema migration — เพิ่ม passCount, failCount ใน ipc_criteria + enum value count_based (SQLite + MySQL)
  • IPCCriteriaForm: เพิ่ม section "ผ่าน/ไม่ผ่าน แบบระบุจำนวน" + 2 input fields with bi-directional auto-calc
  • Validation rules + Zod schema update สำหรับ count_based type
  • IPC Recording page: เพิ่มปุ่ม "✅ ผ่านทั้งหมด" / "❌ ไม่ผ่านทั้งหมด" เหนือ checkbox grid
  • เพิ่ม criteria type branch ใหม่ count_based รองรับใน recording UI (ช่องกรอกจำนวน 2 ช่อง + auto-calc)
  • ปรับ design หน้าบันทึก IPC — sticky header, compact summary, bulk actions, criteria-type indicator badge
  • อัปเดต label/translation keys (th/en) — "ผ่าน/ไม่ผ่าน checkbox (ตรวจสอบแต่ละ sample)" + "ผ่าน/ไม่ผ่าน แบบระบุจำนวน"
  • Service wo-execution.service.ts: เพิ่ม aggregation logic สำหรับ count_based (ไม่ต้อง save ต่อ sample)
  • Unit test + E2E test ครอบคลุม 3 criteria types
⏱ ประมาณการเวลาพัฒนา 10 ชั่วโมง (1-1.5 วัน)

5 Finished Product — รูป Packaging (สติ๊กเกอร์/กล่อง/รูปยาในแพ็ค)

⚠ บางส่วน
หัวข้อ รายละเอียด
ประเด็น / ความต้องการ หน้า Master Data สินค้าสำเร็จรูป (Finished Product) ต้องมีช่องอัปโหลดรูปภาพ packaging แยกประเภท เช่น:
  • สติ๊กเกอร์ติดขวด (Bottle Sticker)
  • กล่องบรรจุภัณฑ์ (Packaging Box)
  • รูปยาที่อยู่ใน package (Product Photo Inside Package)
สิ่งที่ระบบมีแล้ว
  • ตาราง item_images รองรับอัปโหลดรูปภาพ + thumbnail + sort order + description
  • API: GET/POST/DELETE /api/items/[id]/images ครบ (max 5MB, PNG/JPEG/GIF/WebP)
  • Component ItemImagesSection + integrated ใน ItemEditForm แล้ว
  • รองรับ primary image flag
สิ่งที่ระบบยังไม่มี
  • ฟิลด์ imageType (enum: 'general', 'sticker', 'box_front', 'box_back', 'product_photo')
  • UI แยกหมวดรูปภาพตามประเภท (Tabs / Category Filter)
  • Slot อัปโหลดเฉพาะ packaging type สำหรับ FG items
  • Label ภาษาไทย/อังกฤษต่อประเภท image
สิ่งที่ต้องพัฒนา
  • Schema migration — เพิ่ม imageType enum ใน item_images (SQLite + MySQL)
  • ขยาย ItemImagesSection — แยก Tabs ตามประเภท + สลอตเฉพาะสำหรับ FG
  • API เพิ่ม filter ?imageType=sticker + validation enum value
  • Preview layout แสดงรูปทุกมุมใน item detail page
  • Translation keys + i18n th/en
  • Unit test + E2E test
⏱ ประมาณการเวลาพัฒนา 7 ชั่วโมง (~1 วัน)

6 FG Release Workflow — ฝ่ายผลิต → Quarantine → QA/QC ปล่อยผ่าน/Reject

✗ ไม่ผ่าน GMP
หัวข้อ รายละเอียด
ประเด็น / ความต้องการ ต้องมี workflow การปล่อยสินค้าสำเร็จรูปตามมาตรฐาน GMP:
1. ฝ่ายผลิตผลิตเสร็จ → FG เข้าสถานะ "รอตรวจ/กักกัน" (Quarantine)
2. QA/QC ตรวจ → Release (ผ่าน) เข้าคลัง FG ขายได้ หรือ Reject (ไม่ผ่าน)
3. หาก Reject → เลือกห้องเก็บ (ห้อง Reject / ห้องกักกัน / ห้อง Hold / ห้อง Disposal)
4. บันทึก audit trail ว่าใครอนุมัติ/ปฏิเสธเมื่อไหร่
สิ่งที่ระบบมีแล้ว
  • ตาราง inventory_lots มี status field: 'quarantine', 'under_test', 'released', 'rejected', 'blocked'
  • API: PUT /api/inventory/lots/[id]/status เปลี่ยน status ได้
  • Lot เริ่มต้นที่ status 'quarantine' อัตโนมัติหลังผลิต
  • Production Output page สร้าง FG lot หลังจบ WO
สิ่งที่ระบบยังไม่มี
  • Workflow การอนุมัติเฉพาะสำหรับ FG (ตอนนี้ใช้ lot status ทั่วไปร่วมกับ RM)
  • หน้า /quality/fg-release สำหรับ QA review & approve
  • ตาราง master data quarantine_rooms (ห้องกักกัน/ห้อง Reject/ห้อง Disposal)
  • ฟิลด์ qaReviewedBy, qaReviewedAt, quarantineRoomId, rejectionReason ใน inventory_lots
  • Status ใหม่ 'pending_qa' (แยกจาก 'quarantine' ทั่วไป)
  • การบังคับเลือกห้อง Reject ตอน Reject (required validation)
  • FG Release Dashboard แสดงรายการรอ QA review
สิ่งที่ต้องพัฒนา
  • Schema: ตาราง quarantine_rooms + 4 ฟิลด์ใหม่ใน inventory_lots (SQLite + MySQL)
  • Master Data UI: /master-data/quarantine-rooms (CRUD)
  • API: POST /api/quality/fg-release/[lotId] รับ action (release/reject) + roomId + reason
  • หน้า /quality/fg-release — list FG pending QA + ปุ่ม Release / Reject (modal เลือกห้อง)
  • Auto-trigger: WO complete → FG lot status = 'pending_qa'
  • Dashboard KPI: "รอ QA Review X ชิ้น" + Notification
  • Role permission: เฉพาะ QA/QC ทำ release ได้
  • Audit log + Electronic Signature (GMP Part 11)
  • Unit test + E2E test (happy path + reject flow)
⏱ ประมาณการเวลาพัฒนา 18 ชั่วโมง (2-2.5 วัน)

7 QC — นำเข้าผล Lab ภายนอก (External Lab Test Import)

✗ ไม่มีในระบบ
หัวข้อ รายละเอียด
ประเด็น / ความต้องการ QC บางรายการต้องส่งตัวอย่างไปตรวจที่ Lab ภายนอก (เช่น ตรวจ Microbial, Heavy Metals, Pesticide Residues) ต้องสามารถ import ผลการทดสอบจากภายนอกเข้าระบบได้ พร้อม:
  • อัปโหลดไฟล์ PDF รายงาน Lab
  • บันทึกเลข Certificate
  • ระบุ Lab ผู้ตรวจ (จาก master data หรือ free text)
  • กรอกค่าผลการทดสอบลงในระบบเพื่อใช้ตัดสิน pass/fail
สิ่งที่ระบบมีแล้ว
  • ตาราง quality_tests รองรับ test ภายใน ครบ (result, status, testedBy, approvedBy)
  • Test types: 'incoming', 'in_process', 'final'
  • หน้า /quality/tests/new + detail page
  • Document storage / file upload infrastructure พร้อมใช้
สิ่งที่ระบบยังไม่มี
  • ตาราง master data quality_labs (Lab ภายนอกที่ทำสัญญาไว้)
  • ฟิลด์ testSource ('internal'/'external') ใน quality_tests
  • ฟิลด์ externalLabId, externalLabName, externalCertificateNumber, externalReportReceivedDate
  • ตาราง quality_test_attachments เก็บ PDF report + reference
  • UI Toggle "Internal / External" ในหน้ากรอกผล QC
  • Section แนบไฟล์ PDF lab report (drag-drop)
  • หน้า Master Data /master-data/quality-labs
สิ่งที่ต้องพัฒนา
  • Schema: ตาราง quality_labs + quality_test_attachments + 5 ฟิลด์ใน quality_tests (SQLite + MySQL)
  • Master Data UI: /master-data/quality-labs (CRUD + contact info)
  • API: POST /api/quality/tests/[id]/attachments (upload PDF)
  • Quality Test Form: เพิ่ม Toggle "Internal/External" + Section กรอกข้อมูล Lab ภายนอก
  • Validation: External test ต้องมี cert number + lab + attachment
  • Detail page: แสดง PDF preview + Download button
  • Audit log: ใครนำเข้าผล external + เมื่อไหร่
  • Translation keys + i18n th/en
  • Unit test + E2E test (upload PDF scenarios)
⏱ ประมาณการเวลาพัฒนา 20 ชั่วโมง (2.5-3 วัน)

8 eBMR — การตรวจสอบเครื่องแต่งกาย / PPE (Gowning Inspection)

✗ ไม่มีในระบบ
หัวข้อ รายละเอียด
ประเด็น / ความต้องการ eBMR ต้องมี section บันทึกการตรวจสอบเครื่องแต่งกายพนักงาน (Gowning Inspection) ก่อนเข้าพื้นที่ผลิต เช่น ชุดคลุม (Lab Coat), หมวกคลุมผม (Hair Cap), หน้ากาก (Mask), ถุงมือ (Gloves), ที่ครอบรองเท้า (Shoe Covers) — ตามมาตรฐาน GMP ต้องมี supervisor / QA เซ็นรับรองก่อนเริ่มผลิต
สิ่งที่ระบบมีแล้ว
  • Line clearance มี (equipment/room clearance) — wo_cleaning_logs
  • Environmental monitoring มี (temp, humidity) — wo_environmental_logs
สิ่งที่ระบบยังไม่มี
  • ตาราง gowning_logs (ไม่มีเลย)
  • ฟิลด์ checklist: labCoat, hairCap, mask, gloves, shoeCovers, beard cover
  • Supervisor/QA sign-off field
  • Tab "Gowning Inspection" ใน WO execution
  • API /api/production/work-orders/[id]/gowning-logs
  • Pre-production gate: ต้องผ่าน gowning ก่อนเริ่มชั่ง/ผลิต
สิ่งที่ต้องพัฒนา
  • Schema: gowning_logs (workOrderId, operatorId, checkedBy, checkedAt, ppe checklist, status, notes, photo) — SQLite + MySQL
  • API: POST/GET /api/production/work-orders/[id]/gowning-logs
  • UI: Tab "Gowning Inspection" + checklist form + photo upload
  • Dual control: Operator self-check + QA/Supervisor verify
  • Gate: บล็อก material weighing ถ้ายังไม่ pass gowning
  • แสดง section ใน eBMR print/export
  • Audit log + Electronic signature
  • Translation keys + test
⏱ ประมาณการเวลาพัฒนา 13 ชั่วโมง (1.5-2 วัน)

9 Document Mapping — รวมเอกสารกระดาษ + ดิจิทัล สำหรับ eBMR Export

⚠ บางส่วน
หัวข้อ รายละเอียด
ประเด็น / ความต้องการ ออกแบบหน้าจอ Document Mapping ให้ผู้ใช้ map/รวมเอกสาร paper-based (scan PDF เช่น ลายเซ็น supervisor, รายงาน lab ภายนอก) เข้ากับข้อมูลที่บันทึกผ่านระบบ เพื่อ export เป็น eBMR ชุดเดียวที่ครบทั้งกระดาษและดิจิทัล
สิ่งที่ระบบมีแล้ว
  • Document Management module (/gmp/documents/) มี version control
  • ตาราง attachments, documents, documentVersions, documentApprovals
  • CAPA มี attachment upload (/api/capa/[id]/attachments) — ใช้เป็น pattern ได้
  • Batch Records มี field attachments: string[] (แต่แค่ชื่อไฟล์)
สิ่งที่ระบบยังไม่มี
  • ตาราง wo_attachments หรือ wo_document_mapping
  • ฟิลด์ sourceType ('paper_scan' / 'digital' / 'external_lab' / 'signature')
  • ฟิลด์ category (เช่น 'gowning_photo', 'supervisor_signoff', 'external_qc_cert')
  • UI Mapping Page — drag-drop / checkbox เลือกเอกสารที่จะรวมใน eBMR
  • PDF Merge function สำหรับ export เอกสารรวมเป็น 1 ไฟล์
  • Preview ลำดับเอกสารก่อน export
สิ่งที่ต้องพัฒนา
  • Schema: wo_attachments (workOrderId, documentId/fileUrl, sourceType, category, sortOrder, mappedAt, mappedBy, isIncludedInExport)
  • API: POST/GET/DELETE /api/production/work-orders/[id]/attachments
  • หน้า /work-orders/[id]/document-mapping — list + drag-drop order + checkbox include
  • Section แยกตาม category: Gowning, Material Weighing, IPC, External Lab, Signatures, Other
  • PDF Merge library (pdf-lib / pdf-merger-js) รวมเอกสาร digital + scanned paper
  • Export action: Generate eBMR รวม + watermark "Certified Copy"
  • Audit log: ใคร map เอกสารอะไรเข้า eBMR
  • Unit test + E2E test
⏱ ประมาณการเวลาพัฒนา 20 ชั่วโมง (2.5-3 วัน)

10 การบันทึกการตอกเม็ดยา / หัวเข็ม (Tablet Press / Compression Log)

✗ ไม่มีในระบบ
หัวข้อ รายละเอียด
ประเด็น / ความต้องการ บันทึกกระบวนการตอกเม็ดยา (Tablet Compression) — ขั้นตอนสำคัญในการผลิตยาเม็ด ต้องมี:
  • ข้อมูล Punch Tool (รูปทรง ขนาด Embossing)
  • Machine Parameters (แรงกด, ความเร็ว, ความแข็ง Hardness)
  • Weight Variation Check (ค่าเฉลี่ย ±% ต่อเม็ด — ทุก 30 นาที)
  • จำนวน Reject / Defect
  • IPC ระหว่างตอก
สิ่งที่ระบบมีแล้ว
  • SOP Execution (generic) — รองรับบันทึก step ทั่วไป
  • Material Weighing — ก่อนตอกใช้ได้
  • Production Output — หลังตอกบันทึก qty ได้
  • IPC — ใช้บันทึก weight variation ได้
สิ่งที่ระบบยังไม่มี
  • ตาราง tablet_pressing_logs (ไม่มีเลย)
  • ตาราง punch_tools master data (รหัสเครื่องมือตอก)
  • ฟิลด์ compressionForce, speed, hardness, thickness
  • ฟิลด์ weightVarianceMin/Max + actualWeights array
  • ฟิลด์ rejectCount, defectType, defectReason
  • หน้า /production/work-orders/[id]/tablet-pressing
  • หน้า Master Data /master-data/punch-tools
  • Trend chart ของ weight variation ระหว่างกะผลิต
สิ่งที่ต้องพัฒนา
  • Schema: tablet_pressing_logs + punch_tools (SQLite + MySQL)
  • Master Data UI: /master-data/punch-tools (CRUD + shape, size, embossing, condition)
  • Recording UI: /work-orders/[id]/tablet-pressing — parameter form + weight samples input + reject log
  • Auto weight variation check: alert ถ้าเกิน ±5% (configurable)
  • Integration: link กับ IPC test + SOP Execution
  • Trend chart: weight variation ตลอด batch
  • API: POST/GET/PUT /api/production/work-orders/[id]/tablet-pressing
  • Audit log + Electronic signature
  • Export เข้า eBMR section "Tablet Compression Record"
⏱ ประมาณการเวลาพัฒนา 18 ชั่วโมง (2-2.5 วัน)

11 GMP Module Coverage — ครอบคลุมมาตรฐาน GMP 70% (ขาด 6 หมวด)

⚠ 70% Coverage
หัวข้อ รายละเอียด
ประเด็น / ความต้องการ ตรวจสอบว่าหน้าจอทะเบียนและการบันทึกใน GMP Module ครอบคลุมมาตรฐาน GMP ครบหรือไม่ (SOPs, Qualification, Calibration, Maintenance, Environmental, Training, Change Control, Deviation, CAPA, Complaint, Recall, Internal Audit, Validation, Stability, etc.)
สิ่งที่ระบบมีแล้ว (15 หมวด ✓)
  • SOPs / Procedures (/gmp/documents)
  • Preventive Maintenance (maintenance_records)
  • Cleaning Records (wo_cleaning_logs, sanitation_logs)
  • Environmental Monitoring (wo_environmental_logs)
  • Training Records (hr_training_*)
  • Change Control (/gmp/changes)
  • Deviations (/quality/deviations)
  • CAPA (/gmp/capa)
  • Complaints (/gmp/complaints)
  • Recalls (/gmp/recalls)
  • Internal Audit (/gmp/internal-audit)
  • Stability Studies (/gmp/stability)
  • Pest Control (/gmp/sanitation/pest-control)
  • Sanitation (/gmp/sanitation)
  • Document version control + approvals
สิ่งที่ระบบยังไม่มี (6 หมวด ✗)
  • Equipment Qualification (IQ/OQ/PQ) — ไม่มี qualification protocol แยก (มีแค่ calibration date)
  • Calibration Records (ครบ) — มีแค่ lastCalibrationDate ไม่มี cert/frequency/history
  • Management Review — ไม่มีเลย
  • Self-Inspection — ไม่มี (internal audit มี แต่ไม่ใช่ self-inspection checklist)
  • Supplier Qualification — มี approved vendor list แต่ไม่มี qualification record/audit/สัญญา
  • Water / HVAC System Monitoring — environmental log มี แต่แค่ T/H ไม่มี water purity/HVAC pressure
  • Annual Product Review (APR/APQR) — ไม่มีเลย (PQR บางส่วน แต่ไม่ครบ APR template)
  • Validation Protocols (IQ/OQ/PQ) — ไม่มี template แยก (PQR มีบางส่วน)
สิ่งที่ต้องพัฒนา
  • Equipment Qualification — ตาราง equipment_qualifications + IQ/OQ/PQ templates + UI
  • Calibration Records (ครบ) — ตาราง calibration_records + cert upload + schedule + reminder
  • Management Review — ตาราง management_reviews + meeting minutes + action items
  • Self-Inspection — ตาราง self_inspections + checklist master + findings
  • Supplier Qualification — extend approved_vendors + qualification cycles + audits + contracts
  • Water/HVAC Monitoring — extend environmental log schema + water purity, HVAC pressure differential
  • Annual Product Review — ตาราง annual_product_reviews + APR report template + auto data aggregation
  • Validation Protocols (IQ/OQ/PQ) — ตาราง validation_protocols แยก + execution records
  • Update Sidebar navigation เพิ่ม 6 เมนูใหม่ใน GMP module
⏱ ประมาณการเวลาพัฒนา 27 ชั่วโมง (3.5-4 วัน)
