Scenario ที่ template นี้แก้

ปัญหาคลาสสิก เมื่อ 2 user เปิดหน้าเดียวกัน:

❌ ปัญหา:
  • User A กด "อนุมัติปล่อยของ" → status เปลี่ยนเป็น approved ในจอ A
  • User B เปิดหน้าเดียวกันค้างไว้ — ยังเห็น status "รออนุมัติ"
  • User B กดอนุมัติซ้ำได้ → เกิด duplicate approval
  • Stock เคลื่อนไหวผิด, audit log ผิด
✅ หลังแก้:
  • User A กด → User B เห็น status เปลี่ยนภายใน < 1 วินาที
  • Row ที่เปลี่ยนแถบจะกระพริบสีเขียว 1.5 วิ ให้สังเกตได้
  • ถ้า User B กดซ้ำก่อน sync ทัน → server reject พร้อม error ชัดเจน
  • ป้องกันได้ที่ 2 layer — DB guard (atomic) + UI sync (UX)

Template หลัก (Full version)

prompt 
# แก้ปัญหา Multi-User Race Condition + Realtime Sync

## Scenario
ที่หน้า [URL หรือชื่อหน้า] — เมื่อมีหลาย user เปิดพร้อมกัน:
- User A กด [action เช่น อนุมัติ/บันทึก/ปล่อย]
- ข้อมูลในจอ User B ไม่ update — ต้อง refresh manually
- User B กดซ้ำได้ → เกิด duplicate / data corruption

## ความต้องการ
1. **Server-side guard** — ป้องกัน duplicate ที่ DB level
   (atomic UPDATE ... WHERE status='expected_value')
2. **Realtime UI sync** — User B เห็นข้อมูลเปลี่ยน < 1 วินาที
3. **Visual feedback** — row ที่เปลี่ยนกระพริบสีเขียว 1.5 วิ

## Reuse Infrastructure ที่มีอยู่
- ใช้ pattern เดียวกับ /inventory/lots (tab requisitions)
  + /production/work-orders/[id] ที่ deploy แล้ว
- Components: src/lib/realtime/* + use-realtime-topic hook
- ไม่ต้องสร้าง SSE endpoint ใหม่ — ใช้ /api/realtime/[topic]/events

## ขอบเขต
- เพิ่ม topic ใหม่ใน TopicName: '[topic-name]'
- Service ที่ทำการเปลี่ยน status ต้อง publish event
- หน้าที่ต้องการ sync subscribe ผ่าน useRealtimeTopic
- Filter event ตาม id ที่กำลังเปิดอยู่

## ข้อจำกัด
- Backwards-compatible — ไม่กระทบ user ที่ใช้งานปกติ
- ไม่แตะ audit-wrapper หรือ globalThis pattern
- Deploy 5 tenants (metaherb + arjaro + renunakhon + huaikoeng + phonphisai)

## ขั้นตอน
1. วิเคราะห์ผลกระทบ + เสนอ design
2. Add topic + publish + subscribe (TDD with tests)
3. Type check + build clean
4. Update changelog
5. Deploy 5 tenants
6. ทดสอบ end-to-end ด้วย 2 browser sessions

Tips ในการเขียน Prompt

✅ ทำให้ทำงานง่าย

  • ระบุ scenario ชัด — "User A ทำ X, User B เห็น Y" ไม่ใช่ "ข้อมูลไม่ refresh"
  • อ้างอิงหน้าที่ทำเสร็จแล้ว — "เหมือน /inventory/lots tab requisitions"
  • ระบุ scope: server guard, UI sync, หรือทั้งคู่
  • บอก topic name — ใช้ topic เดิม หรือ topic ใหม่?

❌ หลีกเลี่ยง

  • "ทำให้ realtime" — ไม่ระบุว่าอะไรต้อง realtime
  • "ใช้ WebSocket" — ระบบใช้ SSE; ขอเพราะอะไร?
  • "ป้องกัน duplicate" โดยไม่บอกว่าซ้ำได้เพราะอะไร
⚠ บทเรียนจากครั้งก่อน: ขอแบบ ระบุ scope แคบ (เฉพาะหน้า) จะดีกว่า "system-wide realtime ทั้งระบบ" — ครั้งก่อนทำ system-wide แล้ว user ยกเลิกเพราะซับซ้อนเกินไป (50+ topics, audit-wrapper hooks)
